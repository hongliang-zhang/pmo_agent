# PMO Agent 日报格式规范

## 日报目标

PMO 日报不是需求列表导出，也不是 GitLab 活动流水账。日报的目标是在低打扰前提下，帮助 MAAS 平台管理者快速判断：

1. 今天或本周真正发生了什么变化。
2. 哪些风险需要关注、升级或沟通。
3. 哪些飞书项目信息缺失会影响推进判断。
4. 代码交付和需求状态是否同步。
5. 哪些事项证据充分、暂时不需要打扰相关人。

所有结论必须附带证据、置信度或明确标注为待确认推断。

## 读者

主要读者：

- MAAS 平台负责人和 PMO。
- 产品、研发、QA owner。
- 需要审批沟通或项目写回动作的人。

次要读者：

- 运维或平台值班人员，用于确认 PMO agent 是否正常运行。
- 后续接入 z-mono 的 agent/operator。

## 章节结构

### 1. 今日结论摘要

一屏内回答“今天要不要介入”。

字段：

| 字段 | 含义 |
|---|---|
| 总体健康度 | `Red` / `Yellow` / `Green` |
| 重点进展 | 今日或本周有实质进展的需求数 |
| 需关注风险 | P0/P1 风险数量 |
| 信息维护缺口 | 影响推进判断的信息缺失数量 |
| 代码/需求不同步 | GitLab 与飞书项目状态不一致数量 |
| 建议沟通 | 建议发起 check-in 的人数或事项数 |
| 今日判断 | PMO agent 给出的管理动作建议 |

### 2. 需要关注的风险

只展示需要管理动作的风险，不展示全部字段缺失。

字段：

| 字段 | 含义 |
|---|---|
| 优先级 | `P0` / `P1` / `P2` / `P3` |
| 类型 | `Issue`、`Risk`、`Decision`、`Data Quality`、`Mismatch` |
| 需求 | 飞书项目需求标题和链接 |
| 为什么现在关注 | 触发入报的原因 |
| 证据 | GitLab、飞书项目字段、飞书文档、评论或 check-in |
| 建议动作 | 下一步可执行动作 |
| 找谁 | 推荐沟通对象 |
| 置信度 | `confirmed` / `likely` / `unknown` |

分级规则：

- P0：已阻塞交付或线上风险，例如 CI failed、MR blocked、无 owner 且有近期代码进展。
- P1：会影响近期交付判断，例如有代码进展但需求状态未同步、目标/排期缺失且近期活跃。
- P2：信息维护缺口，当前未必阻塞，但会影响后续 PMO 判断。
- P3：低优先级提醒，只进入摘要或附录，不进入主风险表。

### 3. 今日/本周实质进展

只展示有真实证据的进展。

字段：

| 字段 | 含义 |
|---|---|
| 需求 | 飞书项目需求 |
| 当前状态 | 飞书项目状态 |
| 负责人 | 需求 owner |
| 进展摘要 | 以业务语言总结 MR、commit、状态或文档变化 |
| 证据 | 证据数量和主要链接 |
| 下一步 | 已知下一步或待确认点 |
| 置信度 | 结论置信度 |

入报条件：

- 今日或本周有 MR、commit、pipeline。
- 飞书项目状态或字段近期更新。
- 飞书文档或评论提供了新的目标、测试计划、时间或下一步。
- 人工 check-in 回复补充了关键信息。

### 4. 代码有进展但需求未同步

用于发现“研发在推进，但飞书项目没跟上”的事项。

字段：

| 字段 | 含义 |
|---|---|
| 代码证据 | MR、commit 或 pipeline |
| 可能需求 | 匹配到的需求；无法匹配则为空 |
| 不同步点 | 状态、owner、目标、排期或需求缺失 |
| 建议动作 | 补需求 ID、更新状态、确认 owner 等 |
| 置信度 | 匹配和判断置信度 |

### 5. 需求有变化但代码无交付证据

用于发现“需求侧在推进，但还没有代码交付证据”的事项。

字段：

| 字段 | 含义 |
|---|---|
| 需求 | 飞书项目需求 |
| 变化 | 状态、字段、评论或文档变化 |
| 当前判断 | 可能是方案/评审/测试推进，或代码证据缺失 |
| 建议动作 | 是否需要研发补代码证据或更新计划 |
| 置信度 | 结论置信度 |

### 6. 信息维护缺口

只展示影响判断的信息缺失。长期沉积且近期没有变化的普通缺失不进入主表。

字段：

| 字段 | 含义 |
|---|---|
| 优先级 | P1/P2/P3 |
| 需求 | 飞书项目需求 |
| 缺失信息 | 目标、owner、排期、测试计划、下一步 |
| 为什么影响判断 | 缺失信息造成的 PMO 判断风险 |
| 已查来源 | 已查飞书项目、文档、GitLab、评论或 check-in |
| 候选结论 | 从上下文推断出的候选值；没有则写待确认 |
| 建议动作 | 谁补、补到哪里、何时需要 |

### 7. 建议沟通清单

只生成可执行问题，不生成泛泛提醒。

字段：

| 字段 | 含义 |
|---|---|
| 优先级 | P0/P1/P2 |
| 找谁 | 推荐沟通对象 |
| 需求 | 关联需求 |
| 问什么 | 具体问题 |
| 为什么问 | 证据和风险 |
| 期望产出 | 目标、排期、下一步、状态确认等 |
| 打扰策略 | 是否受 quiet hours、重复窗口、每日次数限制 |
| 是否需审批 | 第一版必须为是 |

### 8. 可以不打扰的事项

明确记录低打扰判断。

入报条件：

- 有 owner。
- 有近期进展或明确下一步。
- 没有 P0/P1 风险。
- 没有代码/需求明显不同步。
- 信息缺失不影响近期推进判断。

字段：

| 字段 | 含义 |
|---|---|
| 需求 | 飞书项目需求 |
| 不打扰原因 | 证据充分、已有下一步、暂无风险等 |
| 证据 | 支撑不打扰判断的证据 |

### 9. 附录

附录保留可追溯数据，但不干扰主报告阅读。

内容：

- 全量 GitLab 证据摘要。
- 孤立代码进展。
- 被降噪的长期沉积需求数量和样例。
- 模型分析 artifact。
- worker、审批、写回、check-in 审计入口。

## 信息筛选规则

需求进入主报告需要满足至少一个条件：

1. 窗口内有 GitLab 交付证据。
2. 窗口内有飞书项目状态、字段、评论或关联文档变化。
3. 存在 P0/P1 风险。
4. 存在代码和需求状态不一致。
5. 需要当天沟通或审批。
6. 是用户显式关注的需求。

长期无变化需求默认降噪。只有满足下列条件之一时升级入报：

- 缺 owner。
- 缺目标或排期，并且近期有代码交付证据。
- 状态超过阈值未更新且仍处于开发/测试/上线阶段。
- 有 failed pipeline、blocked MR 或其他阻塞证据。
- 被飞书文档、评论或 check-in 明确提到。

## 什么不应该进入日报主干

- 全量需求平铺。
- 无近期变化、无阻塞、无管理动作的历史沉积需求。
- 没有证据的确定性判断。
- 同一个需求的每个缺失字段逐条刷屏。
- 长链接、长 JSON、原始 API 响应。
- 对同一个人重复问同一个问题。
- 已有明确下一步且没有风险的事项。

## 示例结构

```markdown
# MAAS_平台 PMO 状态核查日报 2026-06-02

## 1. 今日结论摘要

| 项 | 结论 |
|---|---|
| 总体健康度 | Yellow |
| 重点进展 | 5 个需求有交付证据 |
| 需关注风险 | 2 个 P1 |
| 今日判断 | 优先确认 2 个 MR 阻塞和 1 个代码/需求状态不同步 |

## 2. 需要关注的风险

| 优先级 | 类型 | 需求 | 为什么现在关注 | 建议动作 | 找谁 | 置信度 |
|---|---|---|---|---|---|---|
| P1 | Issue | 企业套餐购买 | MR 可能 blocked，且需求缺 owner | 确认 blocker 和 owner | MR author / 产品 owner | confirmed |

## 3. 今日/本周实质进展

| 需求 | 当前状态 | 负责人 | 进展摘要 | 下一步 | 置信度 |
|---|---|---|---|---|---|
| 体验中心-场景示例后台配置 | 开发阶段 | 余鸿逍 | 2 个 MR、2 个 commit 有更新 | 确认联调和测试计划 | confirmed |

## 4. 代码有进展但需求未同步

暂无。

## 5. 需求有变化但代码无交付证据

暂无。

## 6. 信息维护缺口

| 优先级 | 需求 | 缺失信息 | 为什么影响判断 | 建议动作 |
|---|---|---|---|---|
| P2 | 企业账号下知识库问题修复 | 排期、下一步 | 有代码进展，但无法判断 ETA | owner 补下一步和预计完成时间 |

## 7. 建议沟通清单

| 优先级 | 找谁 | 需求 | 问什么 | 期望产出 |
|---|---|---|---|---|
| P1 | 任正阳 | 企业账号下知识库问题修复 | 当前 blocker、下一步和 ETA 是什么？ | 更新飞书项目下一步 |

## 8. 可以不打扰的事项

- claude code 高峰期客户端排队机制：已有代码证据且暂无阻塞，先观察。

## 9. 附录

- GitLab 证据：92 条。
- 孤立代码进展：79 条。
- 被降噪长期需求：35 个。
```
