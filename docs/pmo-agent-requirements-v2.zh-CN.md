## 1. 关键纠偏

上一版文档把 GitHub/GitLab repo 活动放在了需求中心，这是不准确的。PMO Agent 的主对象不应该是 repo，而应该是「需求」。

MaaS 平台的进行中工作主要以飞书项目里的「需求」维度管理。多数需求由产品提出，少数需求由研发直接提出，但它们都应该进入同一个需求状态模型。GitLab open-platform、飞书文档、测试计划、MR、CI 和飞书沟通，都是用来解释和校验需求状态的证据源。

因此，PMO Agent 的产品定义调整为：

> PMO Agent 是一个围绕「需求目标、进展、风险、下一步」持续核查和补全信息的项目管理 agent。它通过飞书项目读取需求状态，通过飞书文档查找方案和测试计划，通过 GitLab open-platform 校验代码交付，通过飞书 IM 做低打扰沟通闭环。

## 2. 产品目标

PMO Agent 要持续回答：

1. 「MAAS_平台」空间里有哪些进行中的需求？
2. 每个需求的目标是否清楚？
3. 每个需求当前处于什么阶段，是否有真实交付进展？
4. 每个需求关联了哪些方案文档、测试计划、GitLab MR、commit、CI 或发布证据？
5. 哪些需求缺目标、缺方案、缺测试计划、缺排期、缺 owner 或缺下一步？
6. 哪些需求存在风险，需要找人确认或推动更新？
7. 每个人当前负责哪些需求，进展如何，有哪些阻塞？
8. 哪些信息已经足够，不需要打扰人；哪些信息必须找相关人补全？

第一版可以先做「PMO 状态核查 agent」，但设计必须能继续演进成完整 PMO Agent，而不是一次性日报脚本。

## 3. 核心事实源

### 3.1 飞书项目：需求事实源

飞书项目空间：

- 空间名称：`MAAS_平台`
- 链接：`https://project.feishu.cn/7358164361912909827_1719375156/story/homepage`
- 主对象：`需求`

PMO Agent 应优先从飞书项目读取：

- 需求标题
- 需求描述
- 状态 / 流程节点
- 负责人
- 提出人
- 优先级
- 排期
- 迭代 / 版本 / 里程碑
- 关联文档
- 关联缺陷 / 测试 / 子任务
- 评论和状态变更记录
- 自定义字段
- 最近更新时间

如果飞书项目字段维护不完整，agent 不能直接判定需求失败，而应进入「信息补全流程」：

1. 先查关联飞书文档。
2. 再查 GitLab 代码活动。
3. 再查评论和历史沟通。
4. 仍不明确时，生成待沟通问题或通过飞书 IM 找相关人补全。

### 3.2 GitLab open-platform：代码交付事实源

需要关注的 repo 不在 GitHub，而在 GitLab：

- GitLab group：`https://dev.aminer.cn/open-platform`

PMO Agent 应读取该 group 下的：

- projects / repos
- branches
- commits
- merge requests
- reviewers / approvers
- discussions / comments
- pipelines
- jobs
- releases / tags
- deploy 相关信息，如果 GitLab 中可获得

GitLab 不是主对象，只是需求交付证据源。代码活动需要尽量映射回飞书项目里的需求：

- 通过 MR title / description 中的需求 ID 或链接
- 通过 branch name 中的需求 ID / 关键词
- 通过 commit message 中的需求 ID / 关键词
- 通过文件路径和模块归属推断
- 通过人和时间窗口辅助匹配
- 通过飞书项目关联字段直接匹配，如果已有维护

当 GitLab 活动无法匹配到任何需求时，应标记为「孤立代码进展」，进入风险或待确认列表。

### 3.3 飞书文档：方案和上下文事实源

很多方案、测试计划、时间计划、背景讨论不会完整维护在飞书项目字段里，而是在飞书文档中。因此飞书文档是 PMO Agent 的重要上下文源。

Agent 应在以下场景读取或搜索飞书文档：

- 需求目标不明确
- 需求描述过短
- 缺少验收标准
- 缺少测试计划
- 排期或里程碑不明确
- 代码进展和需求状态不一致
- 需求风险需要背景解释
- 用户询问「为什么这么做」「方案是什么」「测试计划是什么」

需要支持的文档检索方式：

- 按飞书项目需求关联文档读取
- 按需求标题 / 需求 ID 搜索
- 按模块名、owner、关键术语搜索
- 按最近更新的方案/测试计划筛选

文档读取后，应抽取：

- 背景和目标
- 方案摘要
- 成功标准 / 验收标准
- 测试计划
- 时间计划
- 风险和依赖
- 决策记录
- 未关闭问题

### 3.4 飞书 IM：低打扰沟通闭环

飞书 IM 是 PMO Agent 的沟通和补全渠道，不是第一版就必须自动发送的通知系统。

Agent 需要在以下情况下找人：

- 需求缺目标，且飞书项目和文档中都找不到明确目标
- 需求缺 owner 或 owner 与实际 GitLab 活动不一致
- 需求状态停留太久，但代码或评论显示已有进展
- GitLab MR 卡住，需要确认 blocker
- CI / 测试失败，需要确认处理人和下一步
- 需求信息维护不完整，需要提示相关人更新飞书项目字段
- 需求已经有代码交付，但飞书项目状态没有更新

沟通前必须生成决策理由：

- 要问谁
- 为什么问这个人
- 已有证据是什么
- 缺失信息是什么
- 这个问题是否必须现在问
- 是否超过打扰预算

第一阶段只生成「建议沟通清单」。自动发飞书消息放在后续阶段，且接入前需要和用户确认权限和发送策略。

## 4. 飞书项目 MCP 接入方案

飞书项目 MCP 官方连接方式：

- HTTP OAUTH：`https://project.feishu.cn/mcp_server/v1`
- HTTP HEADER：备用
- STDIO：备用

优先方案是 HTTP OAUTH，因为它更适合授权明确、权限边界清楚的远程 MCP 接入。

官方说明中，飞书项目 MCP 的配置路径是：

1. 在开发者后台开通所需数据读写权限。
2. 开启 MCP 服务开关，生成插件专属 MCP URL。
3. 在目标空间安装插件。
4. AI 通过 MCP URL 调用 tools 处理空间事务。

PMO Agent 对「MAAS_平台」空间的最小权限建议：

- 读取需求列表
- 读取需求详情
- 读取需求字段
- 读取需求评论
- 读取流程节点 / 状态
- 读取关联文档
- 读取关联缺陷 / 测试 / 子任务
- 后续阶段可申请写评论、更新字段、流转状态权限

第一阶段不建议直接申请写权限。先做只读核查，避免 agent 误更新项目管理系统。

当进入飞书项目 MCP 实际接入时，我会提前告诉你需要操作什么。预计需要：

- 确认「MAAS_平台」空间安装 MCP 插件
- 完成 HTTP OAuth 授权
- 确认 MCP client 是否支持该 OAuth 流程
- 如果 OAuth 在当前环境不可用，再选择 HTTP HEADER 或 STDIO
- 明确读取范围和写入权限是否开启

## 5. 需求状态模型

每个飞书项目「需求」都应被归一化成一个需求状态对象。

### 5.1 基础信息

- 需求 ID
- 需求标题
- 需求来源：产品提出 / 研发提出 / 其他
- 所属空间：MAAS_平台
- 所属产品域 / 模块
- 优先级
- 当前状态 / 流程节点
- 创建时间
- 最近更新时间

### 5.2 目标信息

- 目标描述
- 解决的问题
- 目标用户 / 影响对象
- 成功标准
- 验收标准
- 是否目标明确
- 目标置信度
- 目标来源证据：飞书项目字段 / 飞书文档 / 评论 / 人工确认

如果目标缺失，需求不能只被标记为「信息不完整」。Agent 还需要推动解决：

1. 查找相关文档。
2. 查找评论和历史上下文。
3. 生成建议目标草稿。
4. 找提出人 / owner 确认。
5. 提示相关人补充到飞书项目或文档。

### 5.3 责任人信息

- 产品 owner
- 研发 owner
- 测试 owner
- reviewer / approver
- 需求提出人
- 实际代码贡献人
- 当前 blocker 负责人

当飞书项目 owner 和 GitLab 实际活动不一致时，应标记为「owner 可能不准确」，而不是直接覆盖。

### 5.4 进展信息

- 飞书项目状态
- 最新状态更新时间
- 关联 MR 状态
- 最近 commit 时间
- CI / pipeline 状态
- 测试计划状态
- 发布状态
- 实际进展摘要
- 进展置信度

进展判断不能只看飞书项目状态，也不能只看 GitLab commit。必须用多源证据交叉验证。

### 5.5 风险信息

- 目标缺失
- 方案缺失
- 测试计划缺失
- owner 缺失
- 排期缺失
- 状态长期未更新
- MR 卡住
- CI 失败
- 需求状态与代码进展不一致
- 高风险模块被修改
- 依赖未解决
- 即将到期但证据不足

每个风险都应包含：

- 风险级别
- 证据
- 影响
- 建议动作
- 是否需要找人
- 找谁

### 5.6 下一步信息

- 下一步动作
- 负责人
- 预计时间
- 来源证据
- 置信度
- 是否需要补充到飞书项目

如果下一步缺失，Agent 应先从文档、评论、MR 状态推断；仍不明确时再生成沟通问题。

## 6. 信息补全流程

PMO Agent 的关键能力不是发现信息缺失后报错，而是尽量解决信息缺失。

标准流程：

1. 发现缺失或矛盾
   - 目标缺失
   - 排期缺失
   - owner 缺失
   - 测试计划缺失
   - 状态和代码进展不一致

2. 自动查找上下文
   - 飞书项目字段
   - 飞书项目评论
   - 关联飞书文档
   - 飞书文档搜索
   - GitLab MR / commit / pipeline

3. 形成候选结论
   - 可能目标
   - 可能当前进展
   - 可能 blocker
   - 可能下一步

4. 判断置信度
   - 高：多源一致，可直接进入报告
   - 中：可报告但标注“待确认”
   - 低：进入沟通清单

5. 找相关人确认
   - 优先找需求 owner
   - 其次找最近代码贡献人
   - 再找提出人或 reviewer

6. 提示维护系统
   - 如果确认了目标/排期/状态，应提示相关人更新飞书项目
   - 后续阶段可由 agent 自动写评论或更新字段，但必须先确认权限策略

## 7. 阶段路线图

### Phase 0：需求和接入确认

目标：把系统边界、权限、主对象和第一版成功标准确认清楚。

需要完成：

- 确认主对象为飞书项目「需求」
- 确认空间为「MAAS_平台」
- 确认 GitLab group 为 `dev.aminer.cn/open-platform`
- 确认飞书项目 MCP 接入方式优先为 HTTP OAUTH
- 确认飞书文档读取能力和权限范围
- 确认第一版不自动发飞书消息，只生成建议沟通清单
- 确认需求字段清单：状态、owner、排期、优先级、关联文档、测试计划等

交付物：

- v2 需求文档
- 接入清单
- 权限清单
- 第一版验收标准

不做：

- 不写业务代码
- 不自动连接生产系统写数据
- 不自动发消息

### Phase 1：PMO 状态核查 Agent

目标：做出能读取事实源、发现问题、生成核查报告的最小闭环。

需要实现：

- 读取「MAAS_平台」空间里的进行中需求
- 读取每个需求的核心字段
- 读取需求关联文档或文档链接
- 读取 GitLab open-platform 下 repo / MR / commit / pipeline
- 将 GitLab 证据尽量匹配到飞书项目需求
- 生成需求状态卡片
- 检测信息缺失：
  - 缺目标
  - 缺 owner
  - 缺排期
  - 缺测试计划
  - 缺下一步
  - 状态长期未更新
- 检测交付风险：
  - MR 卡住
  - CI 失败
  - 有代码进展但需求状态未更新
  - 有需求推进但没有代码或文档证据
- 生成每日 PMO 状态核查报告
- 生成建议沟通清单，但不自动发消息

输出格式：

- Markdown 报告
- 需求状态表
- 风险列表
- 信息缺失列表
- 建议沟通清单

验收标准：

- 能列出「MAAS_平台」进行中需求
- 能识别每个需求的目标/owner/状态/排期是否完整
- 能把至少一部分 GitLab MR/commit 匹配到需求
- 能明确哪些结论有证据，哪些只是推断
- 能给出“需要问谁、问什么、为什么问”的列表

### Phase 2：上下文增强 Agent

目标：让 agent 不只是发现缺失，还能主动查上下文、形成候选结论。

需要实现：

- 飞书文档搜索和读取
- 需求关联文档解析
- 方案摘要抽取
- 测试计划抽取
- 时间计划抽取
- 目标/验收标准抽取
- 文档内容和飞书项目字段对比
- 文档内容和 GitLab 进展对比
- 对缺失字段生成候选补全文案

典型能力：

- 需求里没有目标，但方案文档里写了目标，agent 能提取并标记来源
- 需求里没有测试计划，但关联文档里有测试计划，agent 能识别
- 飞书项目状态是开发中，但 MR 已合并，agent 能提示状态可能未更新
- 文档写了 5 月 31 日提测，但没有测试进展，agent 能标记风险

输出增强：

- 每个需求的「上下文摘要」
- 每个缺失字段的「候选补全」
- 每个风险的「证据链」

### Phase 3：低打扰沟通 Agent

目标：从“建议沟通清单”升级为“可控地找人确认和补信息”。

接入前需要你确认：

- 飞书 bot 是否可以私聊相关人
- 是否允许发群消息
- 是否允许自动发送，还是必须人工确认后发送
- 每人每天最多问几次
- 哪些风险可以越过预算直接提醒
- 消息中是否允许附带链接和证据摘要

需要实现：

- 人员身份映射：飞书用户、GitLab 用户、飞书项目 owner
- 问题生成策略
- 打扰预算
- quiet hours
- 发送前审批模式
- check-in 答复解析
- 将答复回写到 agent 状态
- 提示相关人更新飞书项目字段

第一版沟通建议：

- 默认人工确认后发送
- 每人每天最多 1 个 PMO 问题
- 同一需求 24 小时内不重复追问
- 只问一个具体问题，不问泛泛的“进展如何”

示例：

> 我看到需求「xxx」当前在飞书项目里缺少验收标准；关联方案文档只写了背景，GitLab 上已有 MR !123。这个需求的验收标准是按文档补充，还是需要你重新确认？如果方便，请直接补到飞书项目。

### Phase 4：项目维护闭环 Agent

目标：让 agent 不只报告问题，还能推动项目系统保持干净。

需要实现：

- 对飞书项目字段完整度打分
- 识别长期维护不完善的需求
- 识别需求状态和实际交付不一致
- 对每个需求生成维护建议
- 在获得权限后，给需求评论补充建议
- 在获得权限后，更新部分低风险字段
- 生成每周项目卫生报告

可自动更新的低风险字段候选：

- 关联 MR 链接
- 关联文档链接
- 最近 GitLab 进展摘要
- agent 生成的风险评论

不建议自动更新的字段：

- 需求目标
- 优先级
- 排期
- owner
- 状态流转

这些字段应由 owner 确认，或至少经过人工审批。

### Phase 5：目标管理和风险预测 Agent

目标：把单个需求状态升级为目标和项目组合管理。

需要实现：

- 目标树：平台目标 -> 产品目标 -> 需求 -> 交付证据
- 需求和目标关联
- 无目标需求识别
- 目标下进展汇总
- 目标风险预测
- 跨需求依赖识别
- 跨人负载识别
- 周报 / 月报 / 里程碑报告

关键能力：

- 发现需求缺目标时，推动 owner 补目标
- 发现多个需求目标重复或冲突时，提示合并或决策
- 发现目标下没有实际交付证据时，提示项目风险
- 发现目标已完成但需求状态未关闭时，提示维护

### Phase 6：完整 PMO Copilot

目标：从状态核查工具演进为持续协作的 PMO Copilot。

可能能力：

- 自然语言查询所有需求状态
- 自动生成日报、周报、里程碑报告
- 会议前自动生成项目材料
- 会议后跟踪 action items
- 自动同步飞书项目、文档和 GitLab 证据
- 支持多项目空间
- 支持组织级指标
- 支持 dashboard
- 支持风险趋势和交付预测

## 8. 第一版报告结构

Phase 1 的日报建议结构：

```markdown
# MAAS_平台 PMO 状态核查日报

日期：YYYY-MM-DD
范围：飞书项目 MAAS_平台 + GitLab open-platform

## 1. 总览

- 进行中需求数
- 今日有进展需求数
- 有风险需求数
- 信息不完整需求数
- 建议沟通人数

## 2. 今日有进展的需求
```

## 12. 当前仍需确认的问题

## 13. 我的建议

我建议第一阶段严格做「状态核查」，不要一开始就做自动项目管理更新。

原因：

- 现在最重要的是建立需求状态模型和事实源映射。
- 飞书项目字段、文档、GitLab 之间的关联质量还未知。
- 自动发消息和自动更新字段都需要组织内信任，不能过早启用。
- 先把报告做准，后续再逐步自动化。

第一阶段结束时，应该能稳定产出：

- 哪些需求在推进
- 哪些需求缺目标
- 哪些需求缺测试计划
- 哪些需求状态和代码进展不一致
- 哪些 GitLab MR 找不到对应需求
- 哪些人需要被问
- 问之前 agent 已经查过哪些上下文

这会成为后续所有阶段的基础。
